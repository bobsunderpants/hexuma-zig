# DOSBox parity harness research report — original DOS Hexuma

Research and harness documentation. The reusable harness lives in
`scripts/dosbox_parity.sh`; scratch captures live under `/tmp/opencode/`. The
original game directory `/home/bob/Downloads/Hexuma/` was only read; all
launches used the copy at `/tmp/hexuma-parity-game/`.

## 1. Environment facts (verified)

| Item | Observation |
|---|---|
| Display | `DISPLAY=:1` is KDE KWin's rootless Xwayland display (`XDG_SESSION_TYPE=wayland`), root `1774x1198`, 24 bpp |
| X extensions | `XTEST` and `XInputExtension` present (`xdpyinfo -queryExtensions`) |
| Emulators | `/usr/bin/dosbox` = Debian `0.75~svn4494`; `/usr/bin/dosbox-x` = `2026.08.31` SDL2 64-bit |
| Image tools | ImageMagick `7.1.2-34`: `import`, `convert`, `compare`, `identify` all work |
| X tools | `xprop`, `xwininfo` present; `xdotool`, `xte`, `wmctrl`, `scrot`, `ffmpeg`, `tesseract`, `gocr`, `xvfb-run` absent |
| Compilers | `gcc`/`cc` present; Xlib headers present; **no** `-lXtst`/`-lXext` dev symlinks (only `.so.6`) |
| Safe version check | `SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy dosbox-x -conf /dev/null -v` prints version without opening a GUI |

Important gotcha: `import -window root <file>` **fails** on this X server
(`import: missing an image filename ... @ error/import.c/ImportImageCommand/1291`),
even with `-screen`. Capture a specific window ID instead; that works reliably.

Plain `dosbox` also needs `SDL_VIDEODRIVER=x11` explicitly here. Without it,
SDL chooses a non-X backend (EGL warnings, process runs but no X window appears).
DOSBox-X usually works with `[sdl] videodriver=x11` in its config, but under the
current KDE Wayland session that setting is not enough: SDL2 can still select
its native Wayland backend. A native Wayland DOSBox window never appears in
Xwayland's `_NET_CLIENT_LIST`, and the stale X11 windows left behind are
`IsUnMapped` with `_NET_WM_STATE_HIDDEN`, so `import -window` cannot capture.
The reliable fix is to set `SDL_VIDEODRIVER=x11` in the launch environment too.
`scripts/dosbox_parity.sh` now does this and also requires `_NET_WM_PID` to
match the DOSBox PID it launched, so stale windows cannot be captured.

## 2. Launching the game

`HEXUMA.BAT` contains exactly:

```
break off
mode con: rate=32 delay=1
hexprg
```

So the harness can either call `hexuma.bat` (faithful to the original launcher)
or call `hexprg` directly. `HEXPRG.EXE` is an MZ DOS executable.

### 2.1 DOSBox-X config (preferred — has AUTOTYPE)

Generated by `/tmp/opencode/dosbox-harness-skeleton.sh`, key sections:

```ini
[sdl]
fullscreen=false
fullresolution=original
windowresolution=original
windowposition=10,10
output=surface          ; SDL blits into an X window pixmap -> ImageMagick can read it
videodriver=x11
autolock=false

showmenu=false

[render]

[cpu]

core=normal

[vsync]

[log]
logfile=/tmp/opencode/hexuma-harness.log

[autoexec]
mount c /tmp/opencode/hexuma-scratch
c:
```

Launch:

```sh

```

`cycles=fixed 3000` + `vsyncmode=off` + `priority=normal,normal` give a stable
emulation rate; `-time-limit 600` is a hard backstop if cleanup fails.

## 3. Scripted keystroke injection

### 3.1 DOSBox-X `AUTOTYPE` (preferred)

`AUTOTYPE` is an internal DOSBox-X shell command (listed in the man page's
Z:\BIN command set). Strings in the binary give the syntax:

```
AUTOTYPE [-list] [-w WAIT] [-p PACE] button_1 [button_2 [...]]
```

Examples embedded in the binary:

```
AUTOTYPE -w 1 -p 0.3 up enter , right enter
AUTOTYPE -p 0.2 f1 kp_8 , , enter
AUTOTYPE -w 1.3 esc enter , p l a y e r enter
```

`-w` = wait in seconds before typing; `-p` = pace in seconds between keys;
`,` is a pause token; key names are mapper button names (`enter`, `esc`, `up`,
`space`, `1`, ...).

**Critical ordering rule:** `[autoexec]` is executed sequentially and the game
blocks until it exits. `AUTOTYPE` must be placed **before** `hexuma.bat`, with
`-w` used to delay injection until the game is in the desired state. Putting it
after `hexuma.bat` silently never runs until the game ends (confirmed: byte-identical
capture to a no-input run).

Multiple injections must be separate `autotype` lines; a second `-w` inside
the same command is not a new delay. The skeleton accepts `|`-separated groups
and expands each into its own `[autoexec]` line:

```sh
./dosbox-harness-skeleton.sh /tmp/opencode/hx-seq2 11 "-w 3 -p 0.3 enter|-w 6 -p 0.3 1"
```

Verified input effects (stable captures, all 320x200):

| Input at ~3 s | colors | mean | MD5 |
|---|---:|---:|---|
| none (transient frame at 8 s) | 221 | 0.2256 | `22c2b84e…` |
| `enter` | 144 | 0.2134 | `e74bf6c5…` |
| `esc` | 48 | 0.1189 | `cc9a5515…` |
| `1` | 34 | 0.1104 | `c6a9c515…` |
| `space` | 34 | 0.1104 | same as `1` |

So AUTOTYPE does reach the game and different keys produce different screens.
Mapping those screens to specific game actions still needs separate RE work.

### 3.2 XTest fallback (works for both emulators and the Zig GUI)

No `xdotool`, but the XTEST extension and runtime `libXtst.so.6` are present.
Scratch helper `/tmp/opencode/xtest-key.c` uses Xlib + locally declared XTest
prototypes (XTest.h is absent) and links against the versioned libraries:

```sh
gcc -O2 -o /tmp/opencode/xtest-key /tmp/opencode/xtest-key.c \
  -lX11 /usr/lib/x86_64-linux-gnu/libXext.so.6 \
  /usr/lib/x86_64-linux-gnu/libXtst.so.6

/tmp/opencode/xtest-key 0x1200036 Return
```

It calls `XSetInputFocus` then `XTestFakeKeyEvent` press/release for each
keysym name. Usage with the harness:

```sh
XTEST_KEYS='Return' /tmp/opencode/dosbox-harness-skeleton.sh /tmp/opencode/hx-xtest 2 ""
```

Timing matters: injecting at 7 s produced the unchanged/no-key screen, while
injecting at 2 s produced the same stable image as AUTOTYPE `enter`
(MD5 `e74bf6c5…`, pixel diff 0). Early injection during the intro is effective;
late injection into the settled screen may be ignored.

## 4. Framebuffer capture and determinism

Window discovery (KWin maintains EWMH client list):

```sh
DISPLAY=:1 xprop -root _NET_CLIENT_LIST
DISPLAY=:1 xprop -id <id> WM_CLASS
# or
DISPLAY=:1 xwininfo -root -tree | grep -i dosbox
```

DOSBox-X **destroys and recreates its X window on video-mode changes** (observed
transition from an initial ID to a new 320x200 window). Do not cache the ID:
resolve it again immediately before each capture.

Capture:

```sh
DISPLAY=:1 import -silent -window "$WIN_ID" /tmp/opencode/frame.png
DISPLAY=:1 identify -format '%wx%h colors=%k mean=%[fx:mean]\n' /tmp/opencode/frame.png
```

Because arbitrary wall-clock timing lands on transient intro frames (two runs
at 8 s with the same nominal settings differed), the skeleton captures
repeatedly at 0.5 s intervals and stops after two consecutive frames differ by
≤ 8 pixels (`compare -metric AE`). Verified reproducibility:

```
hx-s1: capture 6 diff=0, capture 7 diff=0, MD5 e74bf6c5…
hx-s2: capture 6 diff=0, capture 7 diff=0, MD5 e74bf6c5…
compare -metric AE hx-s1-window.png hx-s2-window.png -> 0
```

So the combination `cycles=fixed 3000` + AUTOTYPE at a fixed `-w` +
"wait until stable" produces byte-identical screenshots across runs.

## 5. Comparison against the Zig X11 frontend

The X11 frontend is the `gui` subcommand (not `play --choices`, which is a
terminal frontend). From `/home/bob/Documents/Default Project/hexuma-zig`:

```sh
DISPLAY=:1 ./zig-out/bin/hexuma gui --extracted extracted
DISPLAY=:1 xwininfo -root -tree | grep '"Hexuma"'
# observed: 0x… "Hexuma" 680x720+547+230, EWMH client list also lists it
DISPLAY=:1 import -silent -window "$ZIG_WIN_ID" /tmp/opencode/zig-window.png
```

Verified capture: `680x720`, but only **2 colors** (black/white), mean `0.4758`.
The window contains the text/button layout drawn with the default X GC and the
image rectangle, but in this environment the decoded room picture does not
appear in color. That is a frontend/rendering limitation, not a capture failure.

### Why exact pixel parity is not meaningful

* DOSBox framebuffer is the original 320x200 VGA screen (text + picture + UI in one image).
* Zig GUI is a 680x720 X11 window with its own layout: text lines at top,
  picture area at `x=16,y=96` size `640x192` (logical 320x96 scaled 2x), hotspot
  rectangles and numbered-choice buttons below (`src/ui_x11.zig`).
* No OCR is available, so text cannot be extracted automatically from either image.

Practical parity strategy:

1. Drive the **same logical action sequence** into both (DOSBox-X AUTOTYPE or XTest
   keys; Zig GUI key presses via XTest, since its `KeyPress` handler feeds
   `game.execute(line)`).
2. Capture both windows with `import -window`.
3. Compare *state*, not pixels: for the Zig side, also run
   `./zig-out/bin/hexuma play --choices` and capture its stdout as the semantic
   reference (room description/action list). For the DOS side, compare normalized
   image regions and/or manually transcribed text from the stable frame.
4. If a visual comparison is wanted, crop the DOS picture region and the Zig
   view rectangle (`-crop 640x192+16+96`) and compare after geometry
   normalization; the exact DOS crop offset still has to be determined empirically.

## 7. Limitations and open questions

* `AUTOTYPE` key names are mapper button names; a few were verified (`enter`,
  `esc`, `1`, `space`), but the full key-to-game-action mapping was not established.
* Multiple AUTOTYPE lines execute sequentially, so their `-w` values are cumulative;
  the game's own timed intro means "~3 s" is approximate until the stable-frame step.
* Audio is disabled (`SDL_AUDIODRIVER=dummy`, no sound-card config), so any
  audio-dependent behavior is outside this harness.
* `import -window root` is unusable here; only per-window capture works, and an
  occluded/minimized window may capture stale or blank content.
* XTest injection requires correct focus; it worked with `XSetInputFocus` when
  fired early, but a window manager may still redirect focus in other setups.
* The Zig GUI's monochrome rendering and completely different layout preclude
  direct pixel-diff parity; semantic comparison is the realistic goal.
* Plain DOSBox has no AUTOTYPE and was verified only with XTest-style or manual
  input; DOSBox-X is the better base for scripted parity runs.

## 8. Wayland/Xwayland capture fix in `scripts/dosbox_parity.sh`

The earlier failure was not a DOSBox rendering problem. The session is KDE
Wayland, and `DISPLAY=:1` is KWin's rootless Xwayland display. DOSBox-X's
`[sdl] videodriver=x11` config line did not prevent SDL2 from choosing its
native Wayland backend; the visible game window then never appeared in
Xwayland's `_NET_CLIENT_LIST`. The X windows that the harness found were stale
windows from previous runs, reported by `xwininfo` as `IsUnMapped` and by
`xprop` as `_NET_WM_STATE_HIDDEN`, so `import -window` could not read them.

Fix applied to the harness:

* launch with `SDL_VIDEODRIVER=x11` in the environment, in addition to the
  config setting, so DOSBox-X creates a real Xwayland window;
* require `_NET_WM_PID` to equal the PID launched by the harness, so stale
  hidden or viewable windows cannot be captured;
* discard windows with `_NET_WM_STATE_HIDDEN` and require `Map State:
  IsViewable` before calling `import`;
* queue all `AUTOTYPE` lines before `hexuma.bat` (lines after it run only if
  the game exits) and wait for the cumulative `-w` delay before judging frame
  stability.

Verified after the fix:

```sh
./scripts/dosbox_parity.sh /tmp/opencode/parity-final "" "untersuche kamin;gehe rauf" ""
# original screenshot: /tmp/opencode/parity-final/original.png (ok)
```

The captured frame is 320x200 with `Map State: IsViewable`. With queued input,
e.g. `-w 3 enter`, it is a 144-color gameplay frame rather than the 20-color
intro frame. This establishes a reliable original-frame capture path; mapping
specific typed game commands to original actions remains a separate RE/input
task.

## 9. Reliable command injection through XTest

### 9.1 Why AUTOTYPE was insufficient

A controlled experiment isolated the problem:

| Capture | Input | Result |
|---|---|---|
| `p-clean` | none | 320x200, 221 colors, mean `0.225581` |
| `p-enter` | AUTOTYPE `-w 3 enter` | 320x200, 144 colors, mean `0.213365` |
| `p-text` | AUTOTYPE `enter` then `u n t e r s u c h e space k a m i n enter` | pixel-identical to `p-enter` (`AE = 0`) |

AUTOTYPE therefore changes the screen by skipping the intro and reaching the
command prompt, but the queued letters never reach Hexuma's BIOS `INT 16h`
keyboard reader. Delaying, repacing, digit hotkeys, escape, and space variants
all produced the same frame. The original loop at `0x25206` consumes keys via
`0x3a0ea` (`INT 16h AH=01`) and `0x3a0fc` (`INT 16h AH=00`) with a scan-code
mailbox at `0xf87f`; queued AUTOTYPE events did not populate that path.

### 9.2 XTest solution

`scripts/xtest_input.py` is a ctypes wrapper over `libX11.so.6` and
`libXtst.so.6` (no `-lXtst` symlink or `XTest.h` are needed). It:

1. sends `_NET_ACTIVE_WINDOW`, calls `XSetInputFocus`, and raises the window;
2. re-resolves the window for every action, because DOSBox-X recreates it on
   video-mode changes;
3. uses `XTestFakeKeyEvent` for real key press/release pairs and
   `XTestFakeMotionEvent`/`XTestFakeButtonEvent` for clicks;
4. maps `enter` to `Return`, `space`, German umlaut keysyms, and expands
   unrecognised words into per-character key events; umlauts with no keycode on
   the current X layout fall back to `ae/oe/ue/ss`.

`scripts/dosbox_parity.sh` now accepts:

```sh
# Exact script: WAIT is the delay since the previous action.
XTEST_SCRIPT='10:enter;1:enter;2:untersuche kamin enter' \
  scripts/dosbox_parity.sh /tmp/opencode/parity-cmd "" "untersuche kamin" ""

# Convenience: enters two startup keys, then each command plus Enter.
XTEST_COMMANDS='untersuche kamin;gehe rauf' \
  scripts/dosbox_parity.sh /tmp/opencode/parity-multi \
  "" "untersuche kamin;gehe rauf" ""
```

Timing matters: the first Enter should be around 10 s after launch so DOSBox-X
has completed startup and the intro; the second Enter reaches the command
prompt. `XTEST_DELAY` (default `60` ms) and `XTEST_POST_WAIT` (default `2` s)
tune key pacing and the final capture delay. The input script is saved to
`OUT_DIR/input-script.txt` for reproducibility.

Verified results:

| Script | Capture |
|---|---|
| no injection | 320x200, 221 colors, mean `0.225581` |
| one XTest Enter | 320x200, 144 colors, mean `0.213365` |
| two Enters + typed `untersuche kamin` | 320x200, 116 colors, mean `0.232974` |
| two Enters + typed `untersuche kamin enter` | 320x200, 116 colors, mean `0.232394` |
| two commands (`untersuche kamin`, `gehe rauf`) | 320x200, 124 colors, mean `0.214590` |

The typed command and submitted response produce distinct stable frames, so
semantic parity can now be driven action by action against the same command
list used for `zig play --choices`.

### 9.3 Reading original text from the framebuffer

The `.FON` layout is `256-byte header + 256 x 62-byte records`; each record has
`advance, reserved, height, reserved`, eight 7-pixel rows, and two trailing
metric bytes. On screen the glyphs are drawn with shaded olive colors rather
than the raw `.FON` palette indices. Thresholding pixels with
`r > 80 && abs(r-g) < 14 && 18 <= r-b <= 75` yields a binary glyph mask that
matches the FON bitmaps with proportional advances. `scripts/parity_ocr.py`
uses those masks to score known engine output lines against each captured text
row; it is candidate-driven matching, not general OCR, but it is sufficient to
confirm that a response such as `Mitten auf dem Boden liegt ein Zettel.*`
appears in the original frame.
